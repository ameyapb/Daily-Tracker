# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A single-user daily activity tracker, structured like a Kanban board: freeform user-created lanes hold cards (task name, optional description, optional reminder, status TODO/IN PROGRESS/COMPLETED/DELAYED). Status is independent of lane for user lanes only — dragging a card between two user lanes never changes its status. Two system lanes (DELAYED, COMPLETED) sit alongside user lanes; moving a card into or out of either one is a status transition, not a plain lane move, so it always goes through `setCardStatus`. A card moves into the matching system lane automatically when its status becomes DELAYED or COMPLETED (whether set manually or by dragging the card onto that system lane); DELAYED persists, COMPLETED resets daily (archived, not deleted). Dragging a card out of a system lane onto a user lane, or manually changing its status away from DELAYED/COMPLETED, resets it to IN_PROGRESS and returns it to the user lane it was in before entering the system lane (or the first user lane if that one no longer exists). Reminders fire as an in-app blocking modal (no backend push, no service worker) via a client-side poll against `remind_at`. See [README.md](README.md) for setup/commands/deployment.

Resolved UX decisions (shipped, don't re-derive): no live "flying card" animation on a system-lane transition, the card is simply in the system lane next time the board renders; the DELAYED lane is visually flagged (warm accent + count badge) rather than styled like a plain lane; a fired reminder is a centered blocking modal requiring an explicit action, and multiple reminders firing close together queue into ONE modal listing every fired card with inline per-row Snooze/Complete rather than stacking modals; card creation has two paths as of Phase 19: a name-only inline quick-add input per lane (Enter to create, description/status/reminder left unset) for the common fast case, or "more options..." next to it opens the full modal for description/status/reminder; card *editing* (clicking an existing card) is still always the full modal, never inline/expand-in-place; lane headers are plain text labels only, no user-assignable color.

## Claude Code Instructions

- Make surgical, minimal diffs — don't refactor what isn't broken, but if you see code repeating in 2+ places, extract something reusable.
- ALWAYS FOLLOW DRY — never repeat even a single line of logic; extract duplicated expressions into a named constant, helper, or shared module.
- NEVER USE MAGIC NUMBERS OR STRINGS — polling intervals, snooze durations, status values, lane type identifiers, and other literals that carry meaning must live in a named constant, not be scattered inline.
- Naming — use long, self-explanatory names for functions and variables. No abbreviations unless universally understood (e.g. `id`, `url`).
- Write modular code — keep functions and components small and single-purpose; split a file when it starts covering more than one concern rather than letting it grow unbounded.
- Always add tests for new logic (data-layer functions, status transitions, reminder scheduling, and other non-trivial behavior); update existing tests when you change behavior they cover.
- No unnecessary comments — don't restate what the code already says. Only comment to explain a non-obvious constraint, workaround, or subtle invariant (e.g. why a status transition is guarded a particular way).
- No emojis and no em dashes (—) in code, commit messages, or this file.
- Get rid of dead code as soon as you see it — don't comment it out or leave it "just in case".
- Never introduce new libraries or dependencies without asking first.
- Never change core architecture (lane/card/status model, system-lane behavior, Supabase schema) without asking first.
- Always use existing patterns in `data/` for new Supabase queries — don't invent a second way to read/write the same table.
- If a proposed approach conflicts with an existing pattern in this codebase, call it out before implementing and prefer the existing pattern unless there's a clear, documented reason to change.
- If a task or request is vague or ambiguous, ask a single clarifying question before writing code to avoid rework. For a creative/feature-shaped task where intent genuinely needs exploring, `superpowers:brainstorming` (see below) can help; for a small, unambiguous fix a single direct question is still fine.
- Follow the UX decisions already resolved above in "What this is" (no system-lane transition animation, DELAYED lane visually flagged, blocking reminder modal with queuing, card modal for create/edit, plain lane headers) rather than re-deriving them.
- Keep business logic (status transitions, reminder firing, archiving) out of presentational components.
- Keep this file updated in the same change whenever architecture, conventions, or workflow steps change in later phases.

## Superpowers workflow

This repo has the `superpowers` skill set available for process, on top of the rules above. It's optional, not a mandatory gate — use judgment about when a skill actually earns its cost rather than invoking the full chain on every task. For a small or well-understood change (a clear bug fix, a one-file tweak, anything where the approach isn't in doubt) just make the edit directly.

Reach for a skill when it would clearly help:

- **`superpowers:brainstorming`** - a new feature or behavior change where intent/design isn't already pinned down.
- **`superpowers:systematic-debugging`** - a bug whose cause isn't already obvious, before guessing at a fix.
- **`superpowers:writing-plans`** - a change spanning many files or steps, where writing the plan down first avoids rework.
- **`superpowers:test-driven-development`** - new non-trivial logic (data-layer functions, status transitions, reminder scheduling); still write tests either way per the "always add tests" rule above.
- **`superpowers:executing-plans` / `superpowers:subagent-driven-development` / `superpowers:dispatching-parallel-agents`** - larger or riskier work that benefits from staged review or parallelizing independent pieces.
- **`superpowers:requesting-code-review` / `superpowers:receiving-code-review`** - before considering a non-trivial feature or fix complete, and for triaging feedback once received.
- **`superpowers:verification-before-completion`** - before claiming anything is fixed, working, or passing: actually run it (tests, lint, build, or Playwright per the section below) and confirm the output.
- **`superpowers:finishing-a-development-branch`** - once verified, to decide how the work gets integrated.

`superpowers:writing-skills` is only for authoring/editing skills themselves, not app work.

Avoid `superpowers:using-git-worktrees`: this is a single-user, single-branch app where features ship small and direct - a separate worktree/branch per task is overhead this project doesn't need, and it burns tokens re-establishing context in an isolated workspace. Work directly in the main checkout unless the user explicitly asks for a worktree.

None of this overrides the project-specific rules above (surgical diffs, DRY, no magic numbers/strings, ask before new dependencies or architecture changes, existing `data/` patterns) - those always apply.

## Viewing the app / UI feedback

When asked to look at the site (a URL, "check the UI", "how does X look", a screenshot request, or any UX question that needs visual grounding rather than reading source), use Playwright directly — it's already a devDependency here for the E2E suite, no MCP server or `chromium-cli` needed. Don't try other tools first.

- Write a throwaway `.mjs` script **inside the project directory** (e.g. project root or `e2e/`), not in the scratchpad — Node resolves `node_modules` relative to the script's own path, not cwd, so a script outside the project can't `import { chromium } from 'playwright'`. Delete the script when done; never commit it.
- Minimal pattern: `chromium.launch()` -> `newPage({ viewport })` -> wire up `page.on('console', ...)` and `page.on('pageerror', ...)` before navigating -> `page.goto(url, { waitUntil: 'networkidle' })` -> `page.screenshot({ path, fullPage: true })` -> `browser.close()`.
- Works against both the deployed URL (`https://daily-tracker-omega-sepia.vercel.app/`) and local dev — for local dev, start `npm run dev` in the background first and poll until it responds before navigating; don't just `sleep`.
- Always check console/page errors alongside the screenshot, not just that it rendered.
- Always actually view the resulting screenshot (via the Read tool) before giving UX feedback — don't reason about a screenshot you haven't looked at.

## Architecture Overview

### Supabase schema

**`lanes`** — organizational and system lanes.
- `id` uuid PK, `name` text, `position` integer (sort order, system lanes at `-2`/`-1` so they sort before user lanes; COMPLETED at `-2` and DELAYED at `-1` as of the Phase 17 frontend-audit migration, so COMPLETED renders immediately after user lanes and DELAYED renders last)
- `is_system` boolean, `system_type` text nullable, constrained to `delayed` / `completed`
- Check constraint ties `is_system` and `system_type` together (system lanes must have a `system_type`, user lanes must not)
- Unique partial index on `system_type` (excluding nulls) guarantees exactly one lane per system type
- The two system lane rows are seeded once via migration; the app looks them up by `system_type` at runtime rather than hardcoding their ids

**`cards`**
- `id` uuid PK, `lane_id` FK to `lanes` (cascade delete), `name`, `description` nullable, `remind_at` timestamptz nullable
- `status` text, check constrained to `TODO` / `IN_PROGRESS` / `COMPLETED` / `DELAYED`, default `TODO`
- `position` integer (sort order within a lane), `created_at`, `completed_at` nullable
- `pre_system_lane_id` nullable FK to `lanes` with `on delete set null` - the user lane the card was in immediately before moving into DELAYED/COMPLETED, so a later transition back to TODO/IN_PROGRESS can restore it there instead of stranding the card in a system lane
- Status transitions and the accompanying lane move (into or out of DELAYED/COMPLETED system lanes) are the data layer's responsibility (`data/cards.js`), not a DB trigger — `status`, `lane_id`, `pre_system_lane_id`, and `completed_at` are all set together in the same update

**`cards_archive`** — append-only mirror of `cards` for completed-card history.
- Same fields as `cards` plus `original_card_id` (not a FK, since the source row is deleted) and `archived_at`
- `lane_id` is a nullable FK with `on delete set null` since the original lane may later be deleted
- Populated by the daily COMPLETED-lane reset logic (Phase 7), never updated/deleted afterward

**RLS**: enabled on all three tables with permissive `for all using (true) with check (true)` policies for the `anon` role. This is intentional for a single-user, no-auth app using the publishable key directly — not an oversight.

### Data layer

`src/supabaseClient.js` creates the single Supabase client from `VITE_SUPABASE_URL` / `VITE_SUPABASE_PUBLISHABLE_KEY`. All table access goes through `src/data/`:

- `data/constants.js` - shared literals (`CARD_STATUS`, `SYSTEM_LANE_TYPE`, `STATUS_TO_SYSTEM_LANE_TYPE` and its inverse `SYSTEM_LANE_TYPE_TO_STATUS`, `STATUS_LABEL` display strings, `CARD_STATUS_OPTIONS`, `STATUS_AUTOMATION_POLL_INTERVAL_MS`, `REMINDER_POLL_INTERVAL_MS`, `SNOOZE_DURATION_MS`, `SNOOZE_DURATION_OPTIONS`, `STATUSES_ELIGIBLE_FOR_ACTIVE_REMINDER`) plus the shared `isCardReminderDue(card, now)` predicate (eligible status, `remind_at` set, and passed), used by both `useStatusAutomation` and `useReminderQueue` so the "is this card's reminder due" rule lives in one place. Any new status, system-lane-type, or polling-interval/duration literal belongs here, not inline.
- `data/lanes.js` - CRUD and reorder for `lanes`, plus `fetchSystemLane(systemType)` which looks up a system lane by type rather than a hardcoded id, and `fetchFirstUserLane()` (lowest-`position` non-system lane), the fallback destination when a card leaves a system lane with no `pre_system_lane_id` to restore.
- `data/cards.js` - CRUD, `moveCardToLane` (lane only, status untouched; only valid between two user lanes), `reorderCard`, and `setCardStatus` (the only path that transitions status). `setCardStatus` reads the card's current row first: moving to DELAYED/COMPLETED looks up the matching system lane and sets `lane_id`, `pre_system_lane_id` (the lane the card was just in, preserved rather than overwritten if the card was already in a system lane so a direct DELAYED-to-COMPLETED or COMPLETED-to-DELAYED transition keeps the original lane), `status`, and `completed_at` together in one update; moving away from DELAYED/COMPLETED restores `lane_id` from `pre_system_lane_id` (or `fetchFirstUserLane()` if unset) and clears `pre_system_lane_id`.
- `data/archive.js` - `archiveCard` for `cards_archive`, plus `isFromPreviousLocalDay(isoString, now)`, the local-calendar-day comparison used by the daily COMPLETED reset (deliberately calendar-day, not a rolling 24h window, so the reset lines up with when the user actually expects "today" to end).

New Supabase queries should be added to the matching file in `data/` rather than called ad hoc from components.

### UI layer

- `src/hooks/` - stateful hooks that own loading/mutating a resource and wrap the matching `data/` module (e.g. `useLanes.js` wraps `data/lanes.js`, `useCards.js` wraps `data/cards.js`). Components consume these hooks rather than calling `data/` directly, keeping data fetching and business logic (e.g. computing the next lane's/card's `position`) out of presentational components. `useMutationError()` (Phase 9) is a small shared hook both `useLanes` and `useCards` compose: it exposes `mutationError`/`clearMutationError`/`runMutation(fn)`, where `runMutation` wraps a mutation, clears any previous error, catches a thrown error into `mutationError` state, and rethrows so the calling component can still react (e.g. keep a modal open) without duplicating try/catch/state logic in every mutator. Every mutator in `useLanes` (`createLane`, `renameLane`, `deleteLane`, `reorderUserLanes`) and `useCards` (`createCard`, `updateCard`, `deleteCard`, `moveCardToLane`, `reorderCardsInLane`, `setCardStatus`, `moveCardOutOfSystemLane`) is wrapped in `runMutation`, so a failed Supabase call surfaces via `mutationError` instead of failing silently or crashing as an unhandled rejection. `useCards`'s `updateCard` splits status changes out from other field updates and routes status changes through `setCardStatusRequest` (never a plain field update), since only that path performs the system-lane move. `useCards` also exposes `moveCardOutOfSystemLane(cardId, laneId)`, a composite action used only when a card is dragged out of a system lane onto a specific user lane: it calls `setCardStatusRequest` (to IN_PROGRESS) then `moveCardToLaneRequest` to the exact drop target, since `setCardStatus`'s own restore logic would otherwise send the card to its `pre_system_lane_id` rather than wherever the user actually dropped it. `reorderUtils.js` holds two helpers shared by `useLanes`'s `reorderUserLanes`/`nextUserLanePosition` and `useCards`'s `reorderCardsInLane`/`nextCardPositionInLane`, since both hooks reorder a positioned list the same way: `nextPosition(items, startingPosition)` (highest existing `position` plus one, or the starting position if the list is empty) and `reorderAndDiff(items, orderedIds)` (maps an ordered id list to `{ ...item, position: index }`, returning both the full `reordered` list and the `changed` subset whose position actually moved, so only those get persisted). `usePolling(callback, intervalMs)` is a shared "run now, then on an interval, clean up on unmount" hook used by both `useStatusAutomation` and `useReminderQueue`, since both hooks poll `cards` on a fixed interval; each hook wraps its own polling callback in `useCallback` before passing it in, so the interval doesn't get torn down and rebuilt every render. `useStatusAutomation(cards, setCardStatus)` polls on `STATUS_AUTOMATION_POLL_INTERVAL_MS` via `usePolling`, flipping any card `isCardReminderDue` deems overdue to DELAYED via the same `setCardStatus` path the manual status control uses, so the system-lane move happens the same way either way. `useDailyCompletedReset(lanes, cards, deleteCard)` runs once per mount (guarded by a ref, not an interval - the reset only needs to fire once when the board is opened on a new day) and archives-then-deletes any card sitting in the COMPLETED system lane whose `completed_at` is from a previous local calendar day. `useReminderQueue(cards, updateCard)` polls on `REMINDER_POLL_INTERVAL_MS` via `usePolling` for cards `isCardReminderDue` deems overdue, tracks each card's last-acknowledged `remind_at` in a ref (so a still-overdue card isn't re-queued every poll) and exposes `firedCards`/`snoozeCard`/`dismissCard`; `snoozeCard` updates `remind_at` to now-plus-duration via the plain `updateCard` field-update path (not a status change) and clears the fired state; it fires `playReminderSound` (`src/reminderSound.js`, a Web Audio API beep with no bundled audio asset) once per newly-fired batch, not on every poll. `usePrefersReducedMotion()` reads `(prefers-reduced-motion: reduce)` via `matchMedia` and stays in sync with a `change` listener; it exists for JS-driven animation (currently just `Meadow`'s Lottie playback) that the global CSS `animation-duration: 0.01ms !important` override in `index.css` can't reach, since that only affects CSS animations/transitions, not `lottie-web`'s own render loop. `useBushIdleEvent(enabled)` schedules a single one-shot Lottie play per call: after a random `RABBIT_IDLE_BEHAVIOR_INTERVAL_MS` delay it flips its returned `isPlaying` to `true`, holds it there for `BABY_RABBIT_ANIMATION_DURATION_MS` (the baby-rabbit clip's real length), then flips back to `false` and reschedules the next random delay; passing `enabled: false` (reduced motion) clears any pending timers and keeps it permanently idle. Each `Meadow` bush instance owns its own call so bushes fire independently rather than in lockstep. The completion celebration is tracked centrally in `useCards` rather than as a per-`Card` hook (Phase 15 fix, replacing the original `useCompletionCelebration`): each lane renders its cards through a separate subtree (`Board`'s per-lane `cardsByLaneId` filter), so a card transitioning into COMPLETED and moving into the COMPLETED system lane unmounts its `Card` instance in the old lane's subtree and mounts a new one in the system lane's subtree - any edge-triggered detection living inside `Card`/a per-card hook never saw the transition, since the new instance mounts already-COMPLETED. `useCards` exposes `justCompletedCardId`: `setCardStatus` and `updateCard`'s status-changing path both set it (via internal `flagJustCompleted`) whenever the target status is `CARD_STATUS.COMPLETED`, and it self-clears via `setTimeout(RABBIT_IN_A_HAT_ANIMATION_DURATION_MS)` (cleared/reset if another completion happens before the timeout fires, and on unmount). `Board` passes it down through `Lane` to `Card` as `isCelebratingCompletion={card.id === justCompletedCardId}`, so the flag survives the cross-subtree remount instead of depending on component identity.
- `src/components/` - presentational components, one concern per file, with a co-located `*.css` file (e.g. `Board.jsx` / `Board.css`). Components read state and call hook-provided mutators; they don't talk to Supabase or `data/` directly.
- `Board` (Phase 9) shows a `board__empty-state` message in place of the lane list when there are zero user lanes (a fresh install before the first lane is created), and a dismissible `board__mutation-error` banner (`role="alert"`) when either hook's `mutationError` is set, combining `useLanes`'s and `useCards`'s `mutationError` via `??` since only one is ever relevant at a time; dismissing clears both hooks' error state. Handlers that call a mutator directly from a DOM event (`handleCreateLane`, `handleSaveCard`, `handleDeleteCard`, `handleCompleteReminder`) catch-and-ignore the rethrown error, since `runMutation` has already surfaced it via the banner; `handleSaveCard`/`handleDeleteCard` leave the card modal open on failure rather than closing it, so in-progress edits aren't lost. `Lane`'s `commitRename` and delete-button handler follow the same catch-and-ignore pattern for the same reason.
- `Board` renders lanes left-to-right and owns the create-lane form, the card create/edit modal, the reminder modal, and a single dnd-kit `DndContext` covering both lane reordering and card dragging (within a lane and across lanes) — drag items are discriminated by a `type` field (`LANE_DRAG_TYPE` / `CARD_DRAG_TYPE` in `dragTypes.js`) in each draggable's `data` payload, not by separate nested contexts. Its card-drag-end handler picks the mutation by source/target lane kind: user lane to user lane uses `moveCardToLane` (status untouched); user lane to a system lane uses `setCardStatus` with the status the target system lane maps to (`SYSTEM_LANE_TYPE_TO_STATUS` in `data/constants.js`), but only if the card isn't already at that status; system lane to user lane uses `moveCardOutOfSystemLane` so the card both resets to IN_PROGRESS and lands on the exact lane dropped on; system lane to system lane (dragging DELAYED directly onto COMPLETED or vice versa) is treated as a status change via `setCardStatus` like the user-to-system case. `Lane` renders a single lane's header (rename via double-click, delete, drag handle), its card list (droppable + sortable), and a quick-add row (`lane__quick-add`): a name-only text input that creates a card immediately on Enter via `onQuickCreateCard(laneId, name)` (description/status/reminder left unset), plus a "more options..." button next to it that calls `onCreateCard(laneId)` to open the full `CardModal` instead - this row replaces the earlier "+ Add card" button 1:1, including on system lanes, since the original button had no `is_system` guard either. `Lane` also focuses its quick-add input when `n` is pressed while the lane is hovered (`QUICK_ADD_FOCUS_SHORTCUT_KEY` in `data/constants.js`), skipped while any text input/textarea is focused so it doesn't interfere with typing elsewhere (e.g. the lane-rename field). It is drag-disabled for system lanes (`lane.is_system`). Only user lanes participate in lane reordering; system lanes are always rendered in their fixed position after user lanes. The DELAYED lane's header carries a wilted-leaf mark (`.lane--delayed .lane__header::before`, Phase 14, replacing the earlier sticky-note flag): a `clip-path` teardrop-leaf shape rotated 35 degrees around its stem point so it visibly droops beside the lane name, distinct from the upright sprout mark on completed cards. As of Phase 17, the COMPLETED lane's header carries the mirrored upright treatment (`.lane--completed .lane__header::before`): the same leaf `clip-path` as `.card--completed::after` but without the DELAYED mark's `rotate(35deg)`, so it reads as growing rather than wilting. Both system lanes' count badges (`.lane__badge`) generalize the same way: the base `.lane__badge` styling defaults to `--delayed`, and `.lane__badge--completed` overrides it to `--completed` for the COMPLETED lane. `Card` is a sortable card summary (name, status badge, description preview, formatted reminder time) that opens `CardModal` on click; it also plays a one-off "Rabbit In A Hat" Lottie (driven by the `isCelebratingCompletion` prop from `Board`'s `justCompletedCardId`, gated on `usePrefersReducedMotion()` and disabled for the `isOverlay` drag-preview render so the effect never double-fires) as a small `pointer-events: none` overlay pinned to the card's bottom-right corner when the card's status transitions into COMPLETED. A completed card also gets a small leaf/sprout mark (`.card--completed::after`, Phase 14, replacing the earlier folded-corner triangle): a `clip-path` leaf silhouette filled with `--completed`, pinned to the card's top-right corner. `CardModal` holds create/edit fields (name, description, status, reminder) — reminder input toggles between relative (amount + unit, computed off `Date.now()` at save time) and absolute (`datetime-local`) modes; changing status away from DELAYED/COMPLETED here goes through the same `updateCard` to `setCardStatus` path as everywhere else, so the system-lane-out restore behavior applies to manual edits too. `ReminderModal` is the fired-reminder queue's UI: a centered blocking overlay (no click-outside-to-dismiss, per the UX decisions) with one row per fired card rather than one modal per reminder, each row offering the fixed `SNOOZE_DURATION_OPTIONS` buttons plus a custom-minutes input, and a Complete button that routes through `setCardStatus` the same as the manual status control. `Meadow` is a purely atmospheric, `aria-hidden` woodland strip mounted once at the `Board` root as a sibling to `.board` (not nested inside it, so it never scrolls with board content); it renders a fixed-position 120px strip pinned to the viewport bottom (`MEADOW_STRIP_HEIGHT_PX` in `meadowConstants.js`, also consumed by `Board.jsx` to pad `.board`'s bottom so the strip never covers the last lane row) with a CSS grass-gradient background and `WOODLAND_RABBIT_COUNT` looping `lottie-react` "squeeze bunny" instances, each wrapped in a `div` that owns a CSS keyframe hop-across-the-strip animation (randomized duration/delay per instance, `RABBIT_HOP_DURATION_MS`/`RABBIT_HOP_DELAY_MS`) while the inner `Lottie` plays its own idle/squeeze loop; `pointer-events: none` on the strip keeps it from ever intercepting board interaction. Gated on `usePrefersReducedMotion()`: both the wrapper's hop animation and the Lottie's `loop`/`autoplay` are disabled when reduced motion is preferred, so rabbits render as a single static frame in a fixed position rather than looping or hopping. `Meadow` also renders `WOODLAND_BUSH_COUNT` `BushIdleRabbit` instances at random strip positions: each pairs a CSS-only radial-gradient bush shape (`.meadow__bush`, no image asset) with a "baby rabbit emerging" Lottie clip that's conditionally rendered (not just hidden) based on `useBushIdleEvent`'s `isPlaying`, so the animation only mounts while actually firing rather than looping continuously in the background; disabled by the same `usePrefersReducedMotion()` flag as the hopping rabbits. As of Phase 17, `Meadow` renders one additional dedicated `BushIdleRabbit` at `COMPLETION_BUSH_LEFT_PERCENT` (near the COMPLETED lane's side of the strip) whose `useBushIdleEvent` call also takes a `triggerSignal` (wired to `justCompletedCardId` via `Board`'s `completionSignal` prop) so it pops immediately on card completion in addition to its own ambient random timer, turning the bush-pop from pure wallpaper into a response-to-progress signal per the frontend audit. The other `WOODLAND_BUSH_COUNT` bushes keep purely ambient random firing (`triggerSignal` left at its `null` default).
- Status/reminder display strings and the reminder relative-unit-to-milliseconds mapping are named constants (`STATUS_LABEL`, `CARD_STATUS_OPTIONS`, `SNOOZE_DURATION_MS`, `SNOOZE_DURATION_OPTIONS` in `data/constants.js`; `RELATIVE_UNIT_TO_MS` in `CardModal.jsx`) rather than inline literals.
- Theme tokens (colors, fonts) live as CSS custom properties in `src/index.css` under `:root` (light) and the `prefers-color-scheme: dark` media query, following the "Storybook Meadow" design direction (Phase 13; retired the earlier "Paper Planner" terracotta/muddy-brown-black look, keeping the same paper-warm cream/ink-dark base in light mode): `--bg`, `--surface`, `--ink`, `--ink-muted`, `--rule`, `--accent` (dusty rose/blush, `#d9738c` family, replacing the old terracotta), `--accent-bg`, `--accent-border`, `--accent-text` (a darker rose shade of `--accent`, meeting AA contrast for text use, mirroring how `--accent` itself is reserved for borders/large elements that don't need the full 4.5:1 ratio), `--delayed`, `--delayed-bg`, `--completed`, `--completed-bg`, `--shadow`. Dark mode's base moved from a muddy brown-black (`#211c14`) to a deep forest/moonlit-meadow green-black (`--bg: #16241d`), with `--surface`/`--rule`/`--shadow` re-derived off that base and contrast re-verified; this also makes the `Meadow` strip's green grass gradient (which reuses `--completed`/`--completed-bg`) read as consistent with the page background instead of clashing. Font tokens are `--display` (Fraunces, headings), `--sans` (Inter, body), `--mono` (IBM Plex Mono, reserved for genuinely tabular content like timestamps); the three font families are installed via `@fontsource/*` and imported once in `main.jsx`. Status/lane/count badges (`.card__status`, `.lane__badge`, `.counter`) use `--sans` rather than `--mono` as of Phase 13, since they're short display labels, not tabular data. New status- or lane-specific accent tokens follow the same `--<concept>` / `--<concept>-bg` pairing rather than hardcoding colors in component CSS. Shape/motion tokens (added in the Phase 11 whimsical-game-UI chrome pass, not scoped to light/dark) are `--radius-sm` (8px, form controls and small buttons), `--radius-md` (12px, modals), `--radius-pill` (999px, unused after Phase 14's status-pill pass but left in place since nothing else references it as the "fully round" fallback), `--radius-petal` (asymmetric corner radii, sharp on one diagonal pair and fully round on the other - status/lane badges, Phase 14), and `--bounce` (a spring-like cubic-bezier used as the `transition-timing-function` on hover transforms) - component CSS should reach for these instead of a literal `border-radius`/`cubic-bezier` value. Divider tokens (Phase 14) are `--rule-organic` (a `linear-gradient` that fades `--rule` to transparent at both ends, used as a `background-image` in place of a flat `border` on `.lane` and `.lane__header` so the hairline reads as an organic edge rather than a ruled line) and `--rule-warm` (`color-mix(in srgb, var(--rule) 80%, var(--accent) 20%)`, used as `.card`'s full-perimeter `border-color` since a card needs a closed edge a gradient can't provide); both recompute automatically per color scheme since they reference the live custom properties rather than hardcoding per-theme values. `.board`'s background (`Board.css`) is a layered CSS gradient (soft rose/green radial washes plus a vertical `--bg`-to-`--surface` linear wash) rather than the earlier dotted radial-gradient grid, using only existing tokens.
- `lottie-react` (2.4.1) plays the woodland Lottie animations; it ships no package.json `exports` field, so bundler resolution falls back to `main` (a UMD/CJS bundle) instead of `module` (the ESM build) — CJS-to-ESM interop then wraps the whole module as `default`, so a plain `import Lottie from 'lottie-react'` silently resolves to the module object rather than the component and crashes the render ("Element type is invalid"). Worked around via a `resolve.alias` in `vite.config.js` pointing `lottie-react` at `lottie-react/build/index.es.js` directly, rather than a per-import workaround. Lottie source assets live under `src/assets/lottie/`: the `.lottie` files are dotLottie zips (`manifest.json` + one `animations/*.json`, pure vector) sourced by hand from LottieFiles; each has a corresponding unzipped raw animation JSON for `lottie-react` to consume directly (`Lottie` takes a parsed object via `animationData`, not a `.lottie` file): `squeeze-bunny.json` (from `Squeeze bunny _(.lottie`, used by `Meadow`'s hopping rabbits) and `baby-rabbit.json` (from `Baby Rabbit.lottie`, used by `Meadow`'s bush idle event). `rabbit-in-a-hat.json` (from `Rabbit In A Hat.lottie`) is wired to `Card`'s completion celebration (Phase 12) rather than Phase 11's ambient bush event, since a magician-style pop reads more like a reward than background motion.
- Motion-related literals in `meadowConstants.js` cover both the Phase 11 woodland strip and Phase 12's card/lane micro-interactions (not just the meadow proper, despite the filename): `LANE_IDLE_SWAY_DURATION_MS`/`LANE_IDLE_SWAY_DELAY_MS` (per-lane randomized idle-sway timing, set as CSS custom properties from `Lane.jsx`) and `RABBIT_IN_A_HAT_ANIMATION_DURATION_MS` (the completion-celebration clip's real length, derived from its frame count/rate) sit alongside the rabbit-hop and bush-idle constants. `Lane`'s idle sway is a CSS `@keyframes` animation on `.lane` itself; a `lane--dragging` modifier class pauses it via `animation-play-state: paused` while dnd-kit is actively transforming that lane's inline `transform`, so the two never conflict. `Card`'s drag-overlay lift (`.card--overlay`: elevated shadow, slight rotate/scale) needed no new JS, since dnd-kit's `DragOverlay` already isolates the dragged visual from the (hidden) source card. Phase 15 added `ADD_CARD_IDLE_NUDGE_DURATION_MS`/`ADD_CARD_IDLE_NUDGE_DELAY_MS`, timing a small `add-card-idle-nudge` `@keyframes` bounce on `.lane__add-card` (same randomized-per-lane, CSS-custom-property pattern as the idle sway), spending only the last ~4% of a long 60-100s cycle in motion so the "+ Add card" control reads as an occasional hint rather than continuous motion - the intentional response to Phase 15's "spreading motion budget beyond the meadow strip" goal.
- `src/test/setup.js` stubs `window.matchMedia` with a non-matching default (jsdom has no real implementation) so any component test that mounts a tree using `usePrefersReducedMotion()` doesn't crash; a test that needs to exercise a specific matches value or the `change` listener still installs its own `vi.fn()`-based mock (see `usePrefersReducedMotion.test.js`), which overrides this default for that file.

### Testing

Vitest with React Testing Library (`jsdom` environment, configured in `vite.config.js`, setup file at `src/test/setup.js`). Vitest is pinned at `^4.1.10` (bumped from 3.2.7 in Phase 6) because vitest 3.2.7 bundles an internal `vite-node` on vite 7, which silently drops the React JSX transform when the top-level `vite` is 8 (any `.test.jsx` component test fails with "React is not defined"); vitest 4.x supports vite 8 directly. `@testing-library/dom` is an explicit devDependency since it's a peer dependency of `@testing-library/react`/`jest-dom` that isn't auto-installed under `--legacy-peer-deps`. Test files live next to the code they cover as `*.test.js` / `*.test.jsx`. Mock `supabaseClient.js` rather than hitting a real Supabase project in tests. Hooks in `src/hooks/` mock the `data/` module they wrap (not `supabaseClient.js`) and use `@testing-library/react`'s `renderHook`/`act`/`waitFor`. Presentational components with real logic (`Card`, `CardModal`) get rendered directly with `@testing-library/react`'s `render`/`screen`/`fireEvent`.

**Known dev-machine constraint.** This repo is developed on an 8GB-RAM Windows machine that's typically down to 2-3GB free (WSL, Docker, VS Code, etc. resident), so `npm run test` (full suite, 12+ files) can hit a JS heap OOM in the middle of a run (`FATAL ERROR: ... JavaScript heap out of memory`, worker fork exits) purely from system memory pressure, not a code defect. Signature of the memory-pressure case: the crash lands during jsdom/environment setup with `0ms` reported test time for the file in flight, and which file trips it varies by what else is resident at the time - it is not reliably the same file twice. Before concluding a new hook/component test has a real leak, isolate it (`npx vitest run <file>`) and rerun a few times; if it passes standalone and the only failures are OOM crashes (not assertion failures) when run alongside the rest of the suite, treat it as this known constraint rather than a bug, note it to the user, and move on rather than iterating further on it.

**End-to-end (Playwright).** Config at `playwright.config.js`, specs in `e2e/*.spec.js`. Unlike Vitest, these drive a real browser against the real Vite dev server and a real (dedicated, free-tier) Supabase project reserved for testing — never the production project referenced by `.env`. Credentials for that project live in `.env.test` (gitignored; `.env.test.example` documents the shape). `playwright.config.js` boots the dev server itself via `vite --mode test`, which makes Vite load `.env.test` over `.env`. `e2e/testDbClient.js` builds a Node-side Supabase client from `.env.test` (parsed manually, no `dotenv` dependency) and exposes `resetTestDatabase()`, which deletes all cards, archived cards, and user-created lanes but leaves the two system lanes alone; `e2e/global-setup.js` runs it once before the suite, and the `page` fixture in `e2e/fixtures.js` runs it again before every test so specs never depend on run order. Tests run with `workers: 1` and `fullyParallel: false` since every test shares one database and the board queries all lanes/cards globally, so concurrent tests would corrupt each other's state. dnd-kit drag interactions are driven with raw `page.mouse` move/down/up sequences (not HTML5 drag events, which dnd-kit doesn't use). `e2e/**` and `playwright.config.js` are excluded from oxlint's `react/rules-of-hooks` via `ignorePatterns` in `.oxlintrc.json`, since Playwright's fixture `use` callback is not a React hook and the directory has no React/JSX to lint. E2E specs cover lane CRUD, card CRUD, drag-and-drop between lanes, and status transitions that move a card into a system lane; reminders and the daily COMPLETED reset are implemented but not yet covered by an E2E spec.
